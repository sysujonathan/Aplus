# 桌面版本检查与安全更新

## 日常怎么用

版本窗口先展示状态结论、正在运行的版本、主线版本、检查日期和简明更新摘要。手动检查和自动提醒共用同一个窗口；当天缓存只作为新版线索，程序会在后台自动联网重新确认。满足条件时提供整行高亮的“立即更新并重启”，点击后不再重复询问，自动完成备份、更新和重新打开，成功时明确显示完成结果。不满足条件时按钮禁用并明确下一步。“重新检查”仅用于用户主动再次核对；“更新日志”直接打开离线逐PR日志；分支、完整提交号和本机定制信息收在“技术详情”，不要求普通用户理解Git。

灰色按钮不等于都在等待检查：主线自检进行中时提示稍后重新检查；失败或取消时提示等待项目负责人修复；缺少结果时提示稍后检查，持续缺失则联系提供软件的同事。需要人工安装时按钮直接显示“本次需要人工安装”，说明继续等待或反复检查不会解锁，请联系提供／部署Aplus的同事协助，旧版可继续使用，不要删除行情或交易记录。本机修改、开发安装也分别说明需要保留什么、联系谁；这些文案不放宽原更新许可。同一版本号对应不同代码提交时只说明“同一版本号下有代码修订”，不伪造新编号。

编号规则为日期＋PR号，例 `v2026.10.10.29`；预览版明确标注，不能因为数字更大就允许替换。`release_catalog.json`是唯一编号/摘要源，`docs/更新日志.md`为相同内容的文档视图，测试检查一致。PR1未发布，PR12/13随PR11、PR23随PR22纳入主线，不虚构独立发布。旧1.1.4为功能阶段名。未来PR在清单中追加版本及摘要；正式合入后维护发布状态，精确main提交及CI始终决定是否允许更新，不依据编号大小。

软件内的“更新日志”按新版在前展示：版本标题大号加粗，日期、PR号及发布状态用较淡的小字，每项更新用圆点列出，版本之间以横线分隔。长说明自动换行，窗口缩放时横线随内容宽度调整；不会显示 Markdown 标记或冗长的链接原文。此处仅排版同一份离线版本清单，不改变版本事实、更新许可或交易数据。

“正在运行”在窗口启动时固定记录；磁盘代码在运行中更换时显示旧运行版本并要求完整退出托盘重开，禁用直接更新，不能把磁盘SHA当作已加载新版。旧main没有版本清单时，仅对有完整提交证据的历史版本回溯编号；未知旧版显示未编号，不猜编号。新版清单从检查目标的准确Git提交读取，不拿本机预览的版本号冒充正式新版；编号缺失不放宽Git/CI门槛。

顶栏右侧“版本更新”用于主动检查本地代码与GitHub主线。每次桌面启动并完成首屏显示后，会延迟数秒在后台静默检查；没有新版、离线或验收未通过时不弹窗。软件长时间不重启时，点击“策略扫描”后会顺带进行每日低频检查，每个上海日期最多一次（失败也不反复请求）；一键盘前进入扫描阶段使用同一入口。仅更新行情／补拉不会额外联网检查版本。检查不占行情进度；当天缓存发现新版时会自动进行一次新鲜核验，通过后把按钮改为“有新版 · 查看”，并在任务结束、编辑窗口关闭、桌面可见后弹出可选的软件更新提醒。可选择“立即更新并重启”或“稍后”；不强制更新、不打断任务。Aplus自行安装的本机发行分支若已被正式main完整吸收，会自动迁移并保留受保护启动文件；普通开发分支、未吸收代码或其他修改仍禁用更新并说明需维护者核对。手动点顶栏按钮可立即重新检查，不受每日频率限制。

自动提醒按主线提交号记在 `.git/aplus-update/notice.json`，同一新版跨重启也不反复弹出；选择稍后仍可通过顶栏手动更新。窗口不锁住界面、不抢编辑焦点；托盘隐藏时等恢复后再提示，离线／CI未通过／没有新版不弹更新提醒。提醒本身不写交易数据、不预留更新任务，也不替用户确认。缓存结果不能直接升级时，会先要求重新检查。顶部“使用说明”可离线阅读完整操作规则。

“最新版”只指约定仓库 `sysujonathan/Aplus` 的main当前提交，且该提交最新一轮 `A acceptance` 的main push验收成功。未合并PR、失败／进行中的验收不能成为自动更新目标。本地包含未合并修复时显示“尚未进入主线”，不会回退到较旧main；分叉必须人工核对。本地有修改时提交号不能代表全部正在使用的代码。

显示的本地提交号来自磁盘Git状态。若通过命令行或人工复制在运行中修改过代码，必须从托盘退出并重开，不能把磁盘提交号当成尚未重启进程已加载全部新代码的证明。

本地分支、提交号及Git日志仅供维护核对；普通用户先看版本号与结论。确认“更新并重启”才会更新代码。每天的后台检查和弹出提醒不等于同意更新，重新确认时会重新核验目标及验收状态。

## 哪些情况不会直接PULL

- 行情、扫描、研究或状态核验任务仍在排队／运行／收尾。
- 持仓编辑、截图导入预览等弹窗还未关闭；先保存并关闭它们。
- 默认本地Web端口8517仍被占用或无法核对；先退出Web服务。

- 不是普通Git安装；或本机发行版以外的开发分支、有未吸收代码、其他未提交修改／新增文件及无法证明安全的分叉。
- 新文件会覆盖本地保留文件，或代码路径有链接／子模块。
- 新版缺少或写错 `release_installation.json`，依赖清单与其 SHA-256 不一致，当前数据库版本不在新版声明的可迁移范围内，或副本迁移／新环境验收失败。此时旧代码、旧环境和正式数据库均保持可用，不要求普通用户手工搬数据。
- Git、GitHub或网络检查失败，以及检查期间main又出现新提交。

本地端口确认等待最多3秒：Windows关闭端口可能约2秒才明确拒绝连接。只有明确“拒绝连接”才认可已关闭；连接成功、超时或其他无法确认的结果仍拒绝更新，不把延迟或网络异常当作已退出。

`store.py`按数据兼容边界判断，不再要求所有业务方法原样不变。检查器只读解析两个精确提交的代码，不运行候选代码、不打开业务数据库：模块初始化、数据路径、类结构、Store 初始化，以及连接、事务、通用读写、审计与文件落盘基础设施保持一致；原子临时文件的已验证短文件名调整继续兼容。普通业务方法的查询过滤、返回内容、原表内业务 SQL、字面量可选参数及延迟类型标注可随已验收主线迭代，普通私有辅助方法也可新增，不按回测动作或 PR 编号单独放行。已有 API 不删除；DDL、版本元数据、数据路径重写、动态 SQL、显式事务控制变化、新增生命周期钩子及定义期可执行表达式仍拦截。检查作用于 SQL 调用，不把普通提示里的 create／drop 当作改表。更新阶段不调用业务方法或重写用户记录；新版业务行为由主线评审与测试负责。该静态检查不构成任意代码的安全证明：仍要求官方 main 精确提交自检通过、代码备份、隔离启动预检和目标变化后复核。

2026-10-15 用户明确确认：多人评审后合入官方 main 就是发布审批，本机更新器不再重复审批策略或配置。删除写死的逐版本升级白名单，不要求用户按顺序安装中间版本；MTR、其他策略、配置以及冻结清单的已审核主线变化都沿用同一更新流程。检查、确认、隔离预检后和实际替换前仍核对官方 main 的精确提交及最新一轮主线 push 自检，不能拿 PR 绿测或另一个提交的成功结果替代。

冻结清单在更新中只承担发布包完整性校验：目标清单的文件集合必须与目标 Git 版本的全部 `core/`、`config/` 普通文件完整一致，路径合法、不重复，再逐个核对 SHA-256 与目标 Git 文件字节。漏列、新增但未登记、多列、符号链接或嵌套仓库均不能放行；合法新增、删除、改名只需目标清单同步完整，不恢复旧版本白名单。不再要求旧、新清单之间的策略版本、批准文字、文件集合或基线元信息保持某个写死形态。校验失败显示“新版发布文件校验未通过，等待新版修复”，而不是让用户人工核准策略。运行和计算时的冻结文件校验、开发者修改策略前须取得授权的协作约束不变；本次不修改任何冻结策略或配置代码。

旧版更新器自身若使用整文件拦截，会挡住获取这项修复；只合入新 PR 不能改变正在运行的旧检查器。此类旧安装需由维护者在完整退出后，使用通过测试的独立升级工具按同一套保护核对、备份、预检和更新到已验收主线；不能在运行中热改保护开关，也不能伪造自检通过。升级不重做行情／扫描、不清理运行数据。之后的新版本由软件内入口按实际兼容性判断。

本轮取消的是重复策略审批，不是伪造安装能力。正式版用 `release_installation.json` 把 Python 小版本、锁定依赖的精确摘要、独立环境编号、数据库目标版本和可接受来源版本绑定到同一 Git 提交。没有依赖变化的当前版本可继续使用普通精确锁；一旦依赖文件发生变化，发布提交必须同时提供逐安装包 SHA-256 锁定文件，安装使用 `pip --require-hashes`。清单摘要只证明发布文件本身，不能冒充已下载 wheel 的逐文件校验。普通依赖变化由更新助手直接在 `.git/aplus-update/environments/<环境编号>/` 的最终固定路径创建、安装并验收一套并行环境，以“构建中／可用”标记控制启用，绝不通过移动已创建的虚拟环境来发布；最终路径真实启动成功后才切换启动指针。旧 `.venv` 和旧环境不被覆盖。已有环境只有在解释器路径、Python 版本、清单内每个包版本、`pip check` 和环境身份标记全部一致时才复用，不能仅凭目录名或一次探针认定一致。Python 大／小版本变化只有在本机存在对应且经过验收的解释器时才自动继续；缺少解释器时保留旧版并给维护者明确回执，不在客户端静默下载未纳入发布清单的运行时。

数据库结构变化必须由正式版清单明确声明来源版本、目标版本和迁移标识。更新助手先用 SQLite 在线备份接口生成一致备份，再对副本运行目标 Store，检查 `integrity_check`、`foreign_key_check`、目标 schema、表／索引／触发器边界、受保护账本与行情事实摘要，以及数据库引用行情文件的存在性和 SHA-256；副本演练与正式迁移的结果边界必须一致。记录数只作诊断，不以机械增减代替业务完整性判断。只有副本验收通过才安装代码并迁移正式库。正式迁移、隔离启动或新桌面启动失败时，代码、数据库和环境指针作为一个事务回退；一旦新版正式打开后数据库出现额外写入，自动恢复不得覆盖这些新增交易事实，只能保留现场并阻断启动。清单缺失、来源版本不匹配或完整性证明不足都直接停止，不能把“CI 已通过”当作允许猜测迁移的依据。

维护入口为`tools/maintenance_update.py`，只供维护者从已测试的代码目录运行，必须明确指定旧安装、原数据目录和原Python环境。它仍使用同一独立更新助手，不跳过准确main自检和兼容保护；存在未完成任务、事务日志或其他Aplus／Web进程时停止。原数据库额外备份到受保护的更新回执目录，替换代码前后核对64位SHA-256摘要，只有重启前字节保持一致才记该项验证通过。正常重启可能更新任务状态或界面偏好，不能拿重启后的整个数据库文件摘要冒充业务数据丢失；本轮测试和升级不会删除或回退账本。

本地保留文件保护按新旧提交的跟踪路径核对，覆盖新增、重命名及复制后的目标文件，不依赖Git把差异归为“新增”还是“改名”。即使文件被Git忽略，撞名仍停止更新；确认后及隔离预检完成后再次核对，不能凭旧检查结果覆盖后来出现的保留文件。

不会自动 stash、强制 reset 或清理用户目录，也不会在当前有效环境中直接安装依赖。只有正式清单声明并提供可信哈希锁时，才在新的并行环境安装依赖。对Aplus自行建立的 `codex/local-release-YYYYMMDD` 本机发行分支，更新器会虚拟合并当前提交与精确main目标：只有合并结果相对main不含运行代码差异时，才在独立保护进程中切换main并快进。历史说明、测试和显示用发布记录可由正式main取代，`push.cmd` 原样备份并恢复；尚未合并的功能代码、未知开发分支和其他本机修改不能因此被丢弃。

## 更新过程及数据边界

确认后Service先原子锁定空闲状态，阻止新的业务任务进入；窗口暂时隐藏。独立保护进程就绪后才退出旧桌面，并等待整个旧进程释放Windows单实例保护，绝不在旧进程运行中替换文件。保护进程未就绪则撤销这次许可、恢复原窗口；稍后退出程序不会让已取消的准备偷偷执行。

准备更新期间，托盘的打开／退出暂不执行，但监听继续；只有真正关闭程序才停止监听。准备失败或助手超时后，原窗口和托盘恢复正常，可再次打开界面或退出，不必结束进程来恢复。

先在临时代码目录和全新临时数据仓进行冻结校验、依赖导入及真实Tk桌面构建；依赖变化时直接在最终固定旁路环境完成安装、精确身份校验、`pip check` 和同一启动探针，验收前不启用。数据库变化先验收一致副本。随后重新核验本地和远端状态，仅执行固定提交的快进更新；代码更新后再做隔离启动检查，最后才迁移正式库并使用目标环境重启。正式重启固定使用原Store的运行目录，不因更新改变数据位置。桌面和后端实际启动回执到达才记“更新已提交”并原子切换 `.git/aplus-update/current-python.txt`；仅生成进程不算成功。启动超时但进程仍存活时记为“启动待确认”，保留事务门禁并阻止第二个实例，不强制杀进程、不回退可能已经产生新写入的数据库，也不提前切换日常启动环境。

更新元信息、保护锁、并行环境、原提交代码压缩包、迁移前数据库一致备份和回执位于 `.git/aplus-update/`，不会提交Git。每次关键操作前先原子记录事务阶段、旧／新提交、旧／新环境、数据库备份及校验值。两个启动脚本在启动业务程序前先检查未完成事务：能够证明新版组合一致且已有启动回执时继续提交；新版进程仍在确认时安全阻断；没有启动回执且未发生未知写入时回退；备份损坏、状态未知或部分恢复失败时保留现场并阻断，不以删除 `update.lock` 冒充恢复。用户看到的结论统一为“准备中、可以安全切换、正在切换、启动待确认、更新已提交、已安全回退、恢复失败需人工处理”，技术细节保存在回执。

受保护的 `push.cmd` 也随旧代码备份保存。数据库备份只在清单声明结构迁移时生成，用于本次事务失败回退，不替代用户长期数据备份。不删除行情、成交、持仓、资金流水和研究记录。事务提交后始终保留当前有效版本及最近两个实际可恢复旧版本对应的代码、环境和迁移材料；所有未解决失败事务及其诊断材料继续保留。清理只处理已提交且不再被当前指针或保留事务引用的材料，不清理正式 runtime、用户数据或用户自行建立的备份。

本 PR 交付的是 Git 安装目录内、由当前业务 Python 启动的最小可恢复更新事务。它还不是长期独立于业务 Python 的原生监督器，不支持更新器在业务环境损坏时独立自升级，不提供脱离 Git 工作目录的正式安装包更新，不会自动安装跨版本 Python，也没有实现稳定版／快速版授权自动衔接。因此不能宣称所有普通用户升级场景已经完全一键化；这些属于后续产品化任务，当前遇到相应边界会保留旧版并给出明确回执。

发布清单单独改变 Python、环境或依赖身份也必须触发运行环境核验；没有已验收目标解释器时停止。schema 声明升级必须进入受控迁移，即使 Store 静态比较仍判定兼容；更新前还核对实际数据库版本，未知版本、矛盾声明和降级均停止。正常 main 安装回退后恢复原分支和旧提交，仍可再次从软件内检查更新。

“环境未变”仍需在复用前检查解释器、锁定包版本与 `pip check`。首次遇到没有受管理标记的旧 `.venv` 或解释器时，完成全部检查和启动探针后才在更新元数据目录记录接纳，不改写旧环境；后续复用仍重新核验。受管理环境缺失或不匹配的标记不能通过旧环境接纳绕过。环境编号包含 Python、版本锁摘要；存在逐包哈希锁时再包含该锁摘要，单独修订哈希锁会创建另一个固定环境目录，原环境及恢复材料继续保留。无哈希锁的既有编号保持兼容，但创建新环境仍要求逐包哈希锁。

恢复校验通过 SQLite 读取已提交的逻辑内容，包括未 checkpoint 的 WAL，不能仅凭主数据库 SHA 宣称没有新写入。缺少逻辑证明而存在附属日志时保留现场。新版超过初始启动期限时，更新助手额外限时监督五分钟，迟到回执可自动提交；期限后仍未确认则保留启动门禁，下一次启动由恢复入口继续判断。

首版仅针对单个Windows桌面服务。不能同时运行Web工作台／另一独立服务实例共享同一安装或数据仓；升级前先关闭这些入口。默认Web端口在确认和实际替换前均会核对，有服务监听或核对失败则拒绝；自行改端口的Web／自定义服务仍须主动退出，不以默认端口空闲冒充全机进程检查。代码与启动检查通过，不等于真实账户、真实行情或长期使用均已验收。若主线没有新提交，按钮不会凭空产生版本更新。

## 一键盘前遇到行情缺口

版本提示与行情门禁是两件事。三源同步仅部分完成但 `scan_readiness.scan_allowed` 明确允许时，一键盘前会继续扫描 `eligible_ids` 中的合格股票，问题标的不计算、保留缺口和部分完成回执；忽略提醒不放宽资格。目录／日历等范围核验失败、全部标的受未解决缺口阻断、同步失败或用户终止时，不自动继续。若全体均确认当日停牌，可进入扫描核验但回执为“没有可扫描股票”，不计算策略。扫描阶段仍重新进行本地完整性校验，不以同步回执代替真正的扫描门禁。
