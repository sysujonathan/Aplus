# 桌面版本检查与安全更新

## 日常怎么用

顶栏右侧“版本更新”用于主动检查本地代码与GitHub主线。点击“策略扫描”后会顺带在后台检查，每个上海日期最多一次（失败也不反复请求）；一键盘前进入扫描阶段使用同一入口。仅更新行情／补拉不会联网检查版本。检查先让扫描正常提交，不占行情进度，不弹强制更新窗口；发现新版只把按钮改为“有新版 · 查看”。手动点按钮可立即重新检查，不受每日频率限制。

“最新版”只指约定仓库 `sysujonathan/Aplus` 的main当前提交，且该提交最新一轮 `A acceptance` 的main push验收成功。未合并PR、失败／进行中的验收不能成为自动更新目标。本地包含未合并修复时显示“尚未进入主线”，不会回退到较旧main；分叉必须人工核对。本地有修改时提交号不能代表全部正在使用的代码。

显示的本地提交号来自磁盘Git状态。若通过命令行或人工复制在运行中修改过代码，必须从托盘退出并重开，不能把磁盘提交号当成尚未重启进程已加载全部新代码的证明。

点按钮会显示本地分支、提交号、主线提交及最近最多8条更新摘要。可选择稍后；确认“更新并重启”才会更新代码。每天的后台检查不等于同意更新，重新确认时会重新核验目标及验收状态。

## 哪些情况不会直接PULL

- 行情、扫描、研究或状态核验任务仍在排队／运行／收尾。
- 持仓编辑、截图导入预览等弹窗还未关闭；先保存并关闭它们。
- 默认本地Web端口8517仍被占用或无法核对；先退出Web服务。
- 不是普通Git安装、本地不是main、有未提交修改／新增文件、有未合并本地提交或与主线分叉。
- 新文件会覆盖本地保留文件，或代码路径有链接／子模块。
- 新版涉及依赖、数据库实现 `workbench/store.py` 或冻结策略文件；首版保守要求人工升级验收。
- Git、GitHub或网络检查失败，以及检查期间main又出现新提交。

不会自动stash、强制reset、清理目录、安装依赖或切换开发分支。这些保护也意味着历史上“把新代码复制到旧开发分支”的安装，不能靠一个PULL自动理顺：先备份并核对本地修改，再由维护者对齐。尚未合并的修复不能为对齐而丢弃。

## 更新过程及数据边界

确认后Service先原子锁定空闲状态，阻止新的业务任务进入；窗口暂时隐藏。独立保护进程就绪后才退出旧桌面，并等待整个旧进程释放Windows单实例保护，绝不在旧进程运行中替换文件。保护进程未就绪则撤销这次许可、恢复原窗口；稍后退出程序不会让已取消的准备偷偷执行。

先在临时代码目录和全新临时数据仓进行冻结校验、依赖导入及真实Tk桌面构建，再重新核验本地和远端状态，仅执行固定提交的快进更新。代码更新后再做隔离启动检查。正式重启固定使用原Store的运行目录，不因更新改变数据位置。桌面和后端实际启动回执到达才记“完成”，仅生成进程不算成功；启动尚未确认会明确记录，不强制杀进程。

更新元信息、保护锁、原提交代码压缩包和回执位于 `.git/aplus-update/`，不会写进交易数据库或提交Git。它们是代码恢复材料，不是个人数据备份。不删除行情、成交、持仓、资金流水和研究记录，也不回退正式数据库。隔离启动检查失败时停止或安全返回旧代码；返回旧提交采用游离版本，需人工核对分支，不假装main仍在旧版本。出现上次保护锁时先检查回执，不盲目删除或反复更新。

首版仅针对单个Windows桌面服务。不能同时运行Web工作台／另一独立服务实例共享同一安装或数据仓；升级前先关闭这些入口。默认Web端口在确认和实际替换前均会核对，有服务监听或核对失败则拒绝；自行改端口的Web／自定义服务仍须主动退出，不以默认端口空闲冒充全机进程检查。代码与启动检查通过，不等于真实账户、真实行情或长期使用均已验收。若主线没有新提交，按钮不会凭空产生版本更新。

## 一键盘前遇到行情缺口

版本提示与行情门禁是两件事。三源同步仅部分完成但 `scan_readiness.scan_allowed` 明确允许时，一键盘前会继续扫描 `eligible_ids` 中的合格股票，问题标的不计算、保留缺口和部分完成回执；忽略提醒不放宽资格。目录／日历等范围核验失败、全部标的受未解决缺口阻断、同步失败或用户终止时，不自动继续。若全体均确认当日停牌，可进入扫描核验但回执为“没有可扫描股票”，不计算策略。扫描阶段仍重新进行本地完整性校验，不以同步回执代替真正的扫描门禁。
