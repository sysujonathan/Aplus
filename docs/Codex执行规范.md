# Codex 执行规范

本规范说明如何用最小必要成本完成 Aplus 任务。业务安全边界以 [修改约束](修改约束.md) 的 A01—A11 为准，本规范不得降低这些要求。

## 1. 开工定义

每轮先记录以下四项，再开始实施：

1. **任务类型**：研究、设计、开发、修复、评审或验收。
2. **目标与影响范围**：这次要改变的行为、文件或结论。
3. **不变契约**：本次明确不能改变的策略、数据、接口和用户流程。
4. **完成标准**：最小可交付结果及其验证证据。

额外发现默认写入风险或后续建议，不并入当前实现。只有它直接阻断完成标准时，才扩大处理范围并说明原因。

## 2. 风险等级

| 等级 | 典型任务 | 最小验证要求 |
|---|---|---|
| R0 | 纯文档、注释，以及确定不影响行为的普通格式调整 | 文档一致性、格式检查、Git diff 与受保护文件检查；通常不跑 pytest |
| R1 | 局部 GUI 展示、独立辅助函数、低影响修复 | 目标模块测试，加必要的导入、静态或契约检查 |
| R2 | 行情路由、扫描编排、持久化调用、共享接口、跨模块行为；CI 触发、并发、测试命令、覆盖范围或必需检查产生机制的修改 | 相关模块与相邻契约测试；CI 修改还须验证必需检查名称、触发与取消边界；根据影响面补集成回归 |
| R3 | 冻结策略、数据库 schema、正式交易数据、安全或发布关键链路；可能降低或绕过关键安全门禁的 CI 修改 | 先取得对应授权，再执行专项安全验证和完整回归；未取得安全授权时停止；正式 PR 仍通过必需 CI |

风险由可能造成的业务后果和影响范围决定，不由修改行数决定。无法可靠隔离影响时按更高一级处理。

CI 工作流的行为修改至少属于 R2，不得因文件格式是 YAML 而降级。验证必须说明必需检查能否正常产生、何时触发、哪些条件可能漏跑，以及旧运行何时会被取消；若改动可能削弱或绕过关键门禁，升级为 R3 或停止等待对应安全授权与验证。

## 3. 最小必要阅读

- 每轮读取 `AGENTS.md`，再按任务模块定向读取权威约束和相关文档。
- 优先搜索目标函数、直接调用者、写入边界和相应测试，再读取必要代码片段。
- README、系统地图和大型业务文档只有在模块、接口或背景确实相关时读取。
- 已在本轮读取且未变化的内容不重复加载；避免无目标的全仓搜索和完整文件倾倒。

## 4. 验证选择与证据复用

先查 [模块测试地图](模块测试地图.md)，选择能覆盖本次变化的最小测试集合。测试失败时先判断是产品问题、环境问题还是测试前提错误；没有新证据前不得原样盲目重试。实验和数据检查先用小样本，只有结论不足时才扩大。

已有证据可复用的条件是：适用代码未变、依赖与运行环境相容、数据与配置前提一致、验证步骤完整且结果可追溯。出现以下任一情况时证据失效：

- 被覆盖的代码、调用链或契约已改变；
- 依赖、CI 配置、数据版本或关键环境发生变化；
- 前次运行中断、仅部分完成，或无法确认提交号和条件；
- 本次触及更高风险边界，而旧证据未覆盖该风险。

正式 PR 必须通过 GitHub 必需 CI 才能合并，但这不是 Codex 提交 PR 后继续等待的要求。创建或更新 PR 后，CI 与人工评审在后台并行；Codex 不轮询 Actions。后续 CI 失败由人工发起新的修复任务，修复时先定位原因，不能用删测试、跳步骤或放宽分支保护换取通过。

## 5. 自主执行边界

用户已经授权的普通任务中，Codex 可自主完成必要的定向读取、可逆编辑、验证、特性分支、提交、推送和 PR 创建或更新，不逐项重复请求确认。PR 提交后立即完成交付报告并结束当前任务，不因 CI 尚未完成而拒绝提交、延迟交付或持续监控。

下列事项继续遵守专项授权：冻结策略或清单、正式交易数据、数据库高风险操作、任务范围外的产品行为、自动下单、外部消息发送及其他不可逆操作。所有 PR 必须经过人工检查和明确批准；AI 自评、自动测试和 AI 评审不构成人工批准。Codex 不得启动 Auto-merge，也不得自行合并 PR。

## 6. 研究停止条件

研究在以下条件同时满足时停止：已有证据足以回答目标问题；主要风险和不确定性已说明；继续搜索预计不会改变当前决策。达到条件后交付结论和证据，不以搜索次数、资料数量或报告长度作为质量指标。

## 7. 多人和多 Agent 协作

开工前执行轻量检查：更新 GitHub `main`，查看相关活动 PR，确认是否已有负责人，并检查计划修改的共享文件。一个任务保持一个明确负责人和一个主 PR；发现重复工作时优先合并到既有实现、转为评审或停止重复分支。

修改公共文件时在 PR 中说明接口影响。冲突优先基于最新 `main` 解决；无法可靠判断时交给仓库主人确认。不得强推，也不引入额外任务调度平台。

### 验收记录与公共文档

- 每个 PR 的详细验收记录默认新建在 `docs/验收/YYYY-MM-DD-主题.md`；主题应能独立说明改动，不使用尚未生成或可能变化的 PR 编号作为文件名。PR 描述链接该记录，并保留提交 SHA、验证环境、证据类别、结果与未验收项。
- `docs/版本与验收.md` 保留为历史总览，不作为每个 PR 的必改文件。只有用户明确要求集中发布、版本整理或历史归档时，才从已经合并的独立记录汇总更新；不得为了普通 PR 验收而追加占位段落。
- 两个独立 PR 不因日期、文档编号或预计 PR 编号等待彼此。只有代码或接口存在真实前置依赖时，才在 PR 中写明依赖对象和合并顺序。
- 验收文档发生冲突时，逐段合并并保留双方仍有效的事实、证据和未完成项；不得整份选择“ours”或“theirs”。结论不一致时并列记录适用提交与条件，再交由负责人裁决。
- 用户说明、系统地图、模块测试地图等公共文档仍按实际功能或接口变化更新，不能用独立验收记录替代；纯测试证据变化不应无理由改写这些公共说明。

## 8. 完成与成本报告

交付报告只需包含：实际改动、适用的验证证据、剩余风险或未完成事项，以及为控制成本采取的范围说明。成本项只记录实际发生的全量测试、联网、长等待或大样本操作及其必要性；R0 任务可直接说明只做静态检查，不罗列工具调用次数。明确区分：

- **代码测试**：本地或自动化测试覆盖了哪些代码；
- **真实数据验证**：是否使用真实行情或用户运行数据；
- **GitHub CI**：远端必需检查是否通过；
- **长期实际使用验收**：是否经过跨交易日或持续运行观察。

未执行某类验证时直接写明，不以其他类别的通过结果替代。

三种状态必须分别报告：

- **Codex 交付完成**：PR 已创建或更新，必要的本地验证与交付说明已完成；无需等待 CI。
- **PR 达到合并条件**：最新提交的必需 CI 全部通过，并且人工评审者已经明确批准。
- **PR 已合并**：有权限且获得授权的人已经实际执行合并。
