# 启动提示关闭后的 Tcl 原生闪退

## 基线与问题

- 基线：GitHub main `7217a293329510c252c5e4fbc1f05ad7b8d1f7c4`（11.12.3 的发布提交）。
- 产品与测试实现：`e501ccc30d2e5efd4368fa4c3d1394aa09d5d332`。
- 范围：R2，修复加载提示与主界面交接时的界面资源生命周期；保留加载提示及后台初始化。
- 本机 Windows 应用程序错误记录：2026-11-12 18:40:58、18:44:58（北京时间）两次 `AplusApp.exe 2026.11.12.3` 崩溃，故障模块同为 `tcl86t.dll`，异常 `0x80000003`，偏移 `0xfee74`。更新回执已确认启动成功，故障发生在主界面短暂出现之后。

## 可复现根因

`initialize()` 创建独立 Tk 解释器，后台线程只进行数据初始化与模块导入。原实现收到成功结果后销毁窗口，但 Python 回调闭包、Font、PhotoImage 等仍可能构成持有解释器的循环引用。

在独立子进程运行基线加载函数，然后从普通后台线程调用 `gc.collect()`，稳定得到：

```text
Tcl_AsyncDelete: async handler deleted by the wrong thread
Windows fatal exception: code 0x80000003
```

这证明窗口已关闭不代表解释器已经释放；随后后台回收在错误线程删除解释器，可触发原生终止，Python 的普通异常提示无法捕获。未将复现等同于所有闪退的唯一可能原因，但本次异常指纹与现场一致。

另外，ttkbootstrap 已导入时，经典 Tk 控件会登记主题订阅；销毁加载窗口后订阅及 Style 单例也可能保留旧解释器。重试销毁的按钮同样需要清理。

## 修复

只在 `gui/startup_loading.py` 的退出清理中处理：

1. 结束诊断订阅，沿用原有 watchdog 交接规则；确保加载根窗口已销毁。
2. 清理本加载器登记的主题订阅（含旧重试按钮）；仅当 Style 属于这个根窗口时释放其单例引用，不全局清空其他窗口订阅。
3. 释放加载窗口与闭包中的引用，并在创建解释器的主线程立即收尾回收。
4. 收尾期间短暂暂停自动垃圾回收，防止后台自动回收抢先运行；随后恢复调用前的 GC 开关状态，没有永久禁用 GC。

冻结策略、配置、冻结清单、Store/schema、行情计算、三源规则与更新安全判断没有改动。没有打开或迁移本机正式数据库，没有结束残留图表进程，没有覆盖正式安装。
