# 老更新器安全过渡与连续升级验收

## 场景与安全边界

旧日用安装 `a192515369da647c586a2d7609071cda5bd00d75` 将 `tests/fixtures/tls/emsign-ecc-root-g3.pem` 误当用户敏感文件。修复仅对这一精确路径且内容 SHA-256 为 `36e68e205b53c67c7a013894e0d5c8583063468118d1ce78ecbc2200d1dd185c` 的公开证书放行。私钥、其他 PEM、用户证书与数据库继续拒绝；官方 main、精确 CI、冻结清单、本地修改和归档安全检查继续执行。

过渡包中的 VBS 只负责选择旧安装并调用标准库 bootstrap。bootstrap 获取已验收官方 main 的准确提交，提取到临时目录，调用原 `maintenance_update.prepare()`。维护入口额外绑定 bootstrap 的目标 SHA，防止准备期间目标改变。数据路径沿用原启动配置，不调用 Store 构造器去“找数据”，也不创建新数据库替代原仓。

只读核对发现日用环境缺少 8 个正式锁定组件。新增 `requirements-hashes.txt` 从 PyPI 各锁定版本发布元数据取得 Windows x64 / CPython 3.12 安装包 SHA，版本与原 `requirements-lock.txt` 完全一致。首次引入带哈希发行档案时创建并验收独立环境，保留旧环境。安装错误记录脱敏日志，源 URL 不写入该日志。

## 隔离演练方法

- 从本地 Git 对象建立临时共享克隆，切换到真实历史 `a192515`；候选使用最新 main 加本修复文件产生临时提交。
- CI 结果在候选演练中由测试替身提供，因为候选尚未合并成为正式 main。网络信任门禁另有失败、取消和缺失成功的拒绝测试；生产过渡入口仍真实查询官方 GitHub。
- 使用临时 Store 数据仓，通过实际维护入口、备份和 worker 退出握手完成首次过渡；逐包哈希安装完整独立环境、执行真实冻结校验和 Tk 探针，并在重启前两次核验数据库字节及原始备份不变。
- 启动真实候选桌面与后端，读取实际 `started.json`；使用独立测试互斥锁和定时退出，不影响正在运行的用户桌面。
- 实际执行目标 VBS 的解释器／原运行目录路由（临时启动负载只记录参数，不打开业务库）；真实桌面启动另行验证，避免把路由脚本当完整 GUI 验收。
- 生成下一次普通版本，调用软件内更新控制器入口、真实 prepare_worker 和 worker，完成旧测试进程退出握手、实际代码更新、新桌面回执、环境指针提交及门禁清除。仅 UI 外壳、官方候选 CI 和互斥锁隔离使用测试替身；不跳过依赖、冻结及候选代码检查。
- 后端正常启动可以更新界面／任务元数据，因此重启后核对受保护业务事实及数据仓路径；不把整个 SQLite 字节变化误判为业务记录损坏。

## 演练中发现并修复

1. pytest 长目录下 ONNX 安装触发 Windows 长路径限制：改用与日用安装长度相近的短临时目录；哈希锁的只读解析演练成功，没有通过关闭哈希检查解决。
2. 原 VBS 的 UTF-8 中文被系统代码页误读，实际 cscript 报语句未结束：将提示编码为代码页无关的 Unicode 常量。新过渡 VBS 同样处理。

## 第四轮：长短路径根因确认与闭环

本节是当前结论，前述“尚未定位”保留为旧提交的历史证据。验证基线为 `6f0c283beda06797bbace2d432ebecfe58181299` 加本轮补丁，最终提交号见 PR80 正文。

### 根因与七项答复

1. **路径导致拦截失败已证实。** Windows 实际文件同时使用长目录 `C:\Users\Leo\AppData\Local\Temp\Aplus update aet6h3xk\daily\launch_dashboard.py` 与短目录 `C:\Users\Leo\AppData\Local\Temp\APLUSU~1\daily\launch_dashboard.py`。两个入口的旧字符串判断均为 False，`samefile()` 为 True，`resolve()` 指向同一长路径。Gate 1 另外覆盖了短文件名 `LAUNCH~1.PY` 和大小写变化，不仅替换为另一种字符串比较。
2. **首次完成不等于首次受控。** 失败 run `40866673191` 的 fixture 是 `RUNNER~1`，事务根目录是 `runneradmin`，第二次诊断为 `desktop: {}`；两处相同的旧判断会漏过解析后的命令，回落到未包装的桌面。首次真实桌面仍可生成 ACK，但没有测试退出计时器，也没有登记进程；随后默认单实例锁可阻止第二次桌面。原启动器的冲突分支调用阻塞式 MessageBoxW，符合“进程存活、没有 ACK”的现象。旧 CI 未保存弹窗线程栈，因此不把具体窗口现场冒充直接观测；路径漏拦截已实际复现，单实例拒绝由现有真实 Windows 互斥锁测试验证。
3. **前两轮没有覆盖分支未命中。** 日志、进程登记及清理都放在字符串匹配分支里面；继续调整其中的退出时机和清理无法处理根本没有进入该分支的进程。本地没有强制制造长短路径混用，又只检查 ACK/completed，遗漏了首次接管断言。
4. **两次启动统一接管。** 共同的 `launcher_identity()` 用文件身份判断，`controlled_launcher()` 为每次启动记录原命令、解析路径、旧判断、真实 PID、隔离命令及唯一测试互斥锁。无法证明身份的 `launch_dashboard.py` 立即拒绝，不能落入原始 Popen；合法 pip/探针命令保留原用途。每次必须恰好有一个受控进程，且同时登记到清理集合。
5. **真实 ACK 和提交均通过。** 读取真实桌面／后端产生的 `started.json`，核对 `started=True`、事务 `completed` 及环境指针；没有伪造 ACK、模拟 completed 或修改生产 35/300 秒超时。原备份字节、重启前两次数据核验和后续业务事实核验继续执行。
6. **本轮没有遗留占用。** 四次受控桌面启动均 exit code 0；所有登记的测试进程退出后，fixture 才删除环境，两次均确认删除成功。只清理测试自身的进程树，不按进程名清理用户 Python。消除的是已证实的“漏登记桌面”路径，不承诺任何系统故障都不可能发生。
7. **环境差异仍明确保留。** 本地为 Windows 11 `10.0.26200`、Python 3.12.13；既有 GitHub Runner 为 Windows Server 2025、Python 3.12.10。本轮在本地强制真实 8.3 别名两次独立演练，不宣称新 head 已在 Runner 通过，也没有等待远端 CI。最终仍须最新必需 CI 与人工批准。
