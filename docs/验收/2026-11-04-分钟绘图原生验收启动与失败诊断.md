修复，R1；基于 main `d6591c09aa4a925b55b19e874b5054dac2c165cb`（PR101合并提交）。PR101已结束，无法向已合并PR追加修复，使用独立主线跟进PR；最终 head 见该PR。本次只修改测试探针、对应测试和本文档/测试地图，不改生产图表、行情、策略、Store/schema、正式数据或CI工作流。

## 主线证据与判断边界

- 主线 push `A acceptance` run [41667174190](https://github.com/sysujonathan/Aplus/actions/runs/41667174190)，job `126025493373`：升级预检28 passed；完整pytest **1 failed / 2338 passed**。唯一失败为 `test_native_minute_editor_save_reopen_and_cross_periods`，耗时20.65秒；后续Windows发行工作流跳过。
- 该main合并树与PR101最终 `a3807cf0bbb6c7357828f3c0da8818100ad71063` 无源码差异，不存在合并冲突选错代码的差异。
- 原探针把异常缩成 `repr(exc)`，三个Python断言没有消息，因此远端只留下 `['AssertionError()']`。原始失败究竟是加载超时还是保存数量断言，**现有远端日志不能确定**；不能将推断写成已定位的唯一历史根因。
- 可确认的脆弱点：新建WebView用户目录的首次页面加载仅等15秒。隔离注入真实浏览器DOM加载延迟16秒后，保持原15秒等待，稳定得到 `native WebView page load exceeded 15 seconds`，尚未执行绘图。这复现了慢启动被验收误拒的路径；与远端耗时相符但不据此排除其他原因。

## 最小修复

1. 首次页面加载按真实 `loaded` 事件等待，上限45秒；不是固定停45秒。正常启动仍立即继续。编辑器/API就绪、每次保存确认的原15秒上限及父进程90秒总保护保留。
2. 初次保存和重开数量断言附实际数量；所有异常保留完整Python回溯并写诊断，同时传播给父测试/CI日志。页面未加载时不再调用JS收集诊断，避免诊断本身卡在未就绪页面；诊断文件写失败也保留原错误。不会生成成功回执。
3. 原生验收参数化：正常启动，以及在隔离生成的页面头部注入16秒真实DOM加载延迟。测量浏览器自身延迟，随后仍执行所有绘图/保存/重开断言。延迟只作用于测试临时页面，不修改产品网页；不重试失败用例掩盖结果。
4. 页面始终未就绪的反向用例仍要求失败、保留具体回溯、关闭窗口且没有成功回执。该用例仅替代WebView事件，不以模拟用例代替上述真实Windows/WebView2验收。
