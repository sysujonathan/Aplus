## 阶段 A：根因与修复

原路径 `launch_dashboard.main → AplusMainWindow.__init__ → ToolBar._load_date_options` 在主线程读取日期；首次 idle 回调再执行 `WatchPanel.reload → 每股 latest_market_dataset`、`_load_strategies → MatchList.load_from_store`。`after()` 只推迟调用，没有解除同步查询的阻塞。

新增每个后台任务独占的 SQLite `mode=ro/query_only` 连接，使用现有 LatestRefresh 请求身份和取消；查询及候选准备在后台，应用 Treeview 的操作在 Tk 主线程。关注行情按来源/周期分组、每 400 个代码批量查询，保留原 `end/created/rowid` 排序。候选继续使用原快照校验、引擎/数据/快照输入指纹；出错保留现有列表并提示失败，不把错误当空结果。日期也在后台准备，列表使用最终选定的日期与来源。恢复保存布局先于首次候选自动选中，活动图格优先，保留已有异步图表和 CAS 保存。

### 实测方法与已确认根因

`tools/benchmark_startup.py` 只接受带 `startup-probe-isolated.json` 的副本；源为已完成静态备份，原库只读，历史行情复制后使用。探针用真实 Tk/Windows WebView2，关闭实时供应商轮询，避免联网及网络波动。不是新安装 EXE，也不是行情网络测速。冷启动指独立新进程，不声称清空了 Windows 文件缓存。

修复前故意注入 1 秒慢读：新增三个测试全部失败；关注与候选分别占用 Tk 1.088/1.132 秒，读取失败未显示。修复后三个测试通过。

初步实际数据副本：15 个关注、11,741 条观察、79,401 条 dataset 元数据。单次阶段 A 试跑主窗口 2,357 ms 显示；日期准备 2,013 ms、关注准备 950 ms、候选准备 2,007 ms 均在后台。仍有原生控件/图表应用回调约 594 ms，不宣称已经达到 200–300 ms 目标。重复样本汇总与最终阶段 B 证据在后续提交补充。

## 不变边界

## 阶段 B：真实阶段提示与安全生命周期

原生 Tk 小面板约 300×155（100%）、深底细边框和 Windows 小圆角，使用正式 `icon_aplus.ico`（与 `assets/brand/aplus.ico` 同一资源）。图示 24 根合法 OHLC 仅表示等待；白涨蓝跌、灰色底，2.6 秒无可见光束的扫描和淡出循环，不显示百分比、不启动额外 WebView。文字固定坐标并单行截断；只有实际 `span(..., state=started)` 事件改变阶段。

| 真实事件 | 提示 |
|---|---|
| `installed.integrity` / `backend.service` | 正在验证策略与运行配置… |
| `installed.binding` / `backend.store` | 正在读取本地交易数据… |

尚未进入具体阶段时只显示“正在准备交易工作台…”，不提前宣称已经读取数据库。

安装预检及后端/GUI 模块导入在初始化工作线程运行；原数据绑定失败仍进入原有人工选仓/恢复流程，未降低门禁。初始小面板只覆盖核心初始化，工作台创建后不等待余下图表；关注、匹配和日期保留区域提示，读取失败可点击提示重试。没有嵌套 update/sleep 维持动画。原有关闭/保存握手保持不变。

安装版原有 `rotate_backups()` 调用推迟到列表和活动图表就绪、心跳空闲后再在后台执行；没有修改轮转模块、保护指针、最新备份校验或删除规则。初始化期间 ESC 等待工作安全结束，不强杀可能正在迁移的线程。

启动记录 `%TEMP%/aplus_startup.jsonl` 可通过 `APLUS_STARTUP_TRACE=0` 关闭，或 `APLUS_STARTUP_TRACE_PATH` 指定输出；事件只记录阶段、线程、时间、CPU、进程 I/O 与数量，不含行情行、持仓或回调局部变量。Windows 从进程创建时间计时；早期 watchdog 在主窗口构造之前已经运行，沿用原 watchdog 交接。关闭计时不关闭真实阶段通知。

## 最终 Windows 对照

正常 Windows 用户会话，Windows 11 build 26200，Python 3.12.13 / NumPy 2.5.3 / pandas 2.3.3，同一独立行情副本、相同日期/来源/布局和关闭实时供应商轮询的条件。源码入口 + 真实 Tk/WebView2，不是新安装 EXE 的发布验收。基线为开工 main `70db3e5`，实现为已同步 PR153 的 `0a383c3fd2265d6a21416640bc1d9551488c946a`；其后产品代码仅校准初始阶段文字，未改变加载路径。PR153 盘中计算收益不计入本表，探针不发起实时行情/更新检查。

### 异常证据不能删除

早期受限会话中，2026-10-14的339条实际匹配结果，新旧关注/候选/布局摘要一致，但两者均出现约10秒的原生消息循环停顿，新版外层探针退出超时。堆栈停在 Tk 的原生 mainloop，没有证据把它归因为某条 Python 查询。另有受限会话普通场景异常退出。随后正常 Windows 用户会话的20次全部成功退出，没有同类10秒停顿；**原因未确定**，不能仅据此认定已修复。339条历史日期在正常会话的重复与退出须由独立Muse优先复核，尚不具备该场景的可靠p95。

早期300关注夹具两轮成员/排序不一致的成绩已作废：一次误恢复归档条目，一次跨秒更新时间改变排序。同一稳定数据库上，原版关注读取与新批量读取300条逐字段一致；夹具修正和跨秒测试均已提交。历史日期必须能在当前来源选中，不允许拿旧日期冒充请求日期。
