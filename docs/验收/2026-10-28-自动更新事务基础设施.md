# 自动更新事务基础设施验收记录

## 使用影响

普通用户仍从软件内点击更新，不配置额外数据目录，也不手工复制数据库。未来同一 Python 版本内的依赖变化可在最终固定旁路环境安装并验收；未来数据库结构变化必须先在正式库的一致副本上迁移成功，才允许更新正式库。更新中断后，下次由启动器先完成继续提交、安全回退或阻断判断，不删除遗留锁后直接启动。

本 PR 只建立上述能力：不修改当前依赖版本、不修改数据库 schema、不读取或迁移真实用户数据，也不修改冻结策略。

## 不变契约

- GitHub main 精确提交及其 `A acceptance` 成功仍是更新许可前提。
- 本地修改、开发分支、受保护路径、冻结清单异常和不安全归档继续阻断自动更新。
- 正式数据库 schema 仍只由 `workbench/store.py` 管理。
- 运行数据目录不随代码版本变化；更新器不删除行情、成交、持仓或研究记录。
- 所有 PR 仍须人工明确批准后才可合并。

## 实施证据

- `release_installation.json` 将 Python 版本、依赖锁摘要、环境编号、schema 目标及迁移范围绑定到发布提交。
- 依赖变化要求逐包哈希锁，直接在最终固定旁路路径创建虚拟环境，并核对解释器、包版本、`pip check` 和真实启动；成功启动后才写环境指针。
- schema 变化先生成 SQLite 一致备份，在副本运行目标 Store，并检查完整性、外键、schema 对象、受保护业务事实和外部行情文件摘要；正式迁移结果须与副本演练一致。
- 事务文件在关键动作前记录阶段、旧／新代码与环境身份、数据库备份和校验值；启动器在业务启动前恢复未完成事务。
- Popen、迁移验证、环境指针及其他提交前异常进入同一回退路径；部分回退失败保留现场并阻断。
- 新版启动超时且仍存活时保持“启动待确认”，不开放第二实例；新版已经写入正式库后不自动覆盖新增记录。
- 提交后保留当前版本、最近两个可恢复旧版本及全部未解决失败事务；只清理未被引用的已提交历史材料。

## 未验收与后续边界

- 本轮没有使用真实交易数据；真实数据迁移仅在未来某个正式 schema 变更版本中按该版本的专项验收执行。
- 当前 worker 仍由业务 Python 启动，元数据仍位于 Git 目录；尚未交付独立原生监督器、更新器独立自升级、脱离 Git 的安装包更新、跨版本 Python 自动安装和稳定／快速版授权自动衔接。
- 本轮不下载新的 Python 运行时。Python 版本变化只有在设备已有对应解释器且发布流程另行验收时才继续；可信运行时的签名分发属于后续独立任务。
- GitHub CI 和长期跨版本使用验收不由本地测试替代。

## 最终边界修订（基于 3c213ed）

- 环境决策比较源／目标 Python、环境编号、依赖锁和逐包哈希锁身份；清单单独改变运行时也会核验。缺少已验收解释器时停止，未变环境不重复创建。
- 普通 main 和受管理发行分支回退后恢复原分支身份，定向测试覆盖再次检查并成功安装同一正式目标。
- schema 声明变化直接触发受控迁移，更新前校验正式库实际版本；副本没有实际迁移能力、来源不支持或降级均停止。
- Store 没有强制切换 SQLite 日志模式，新库默认 DELETE；已有库可能保留 WAL。迁移和恢复通过同一 SQLite 读取事务计算全库逻辑摘要，纳入未 checkpoint 的已提交 WAL。未知日志或新增交易事实阻止覆盖；单纯 checkpoint 不改变逻辑事实，不误阻断安全恢复。
- 初始启动超时后助手额外限时监督五分钟，迟到回执自动提交，期间不启动第二实例；仍未确认时保留门禁与恢复材料。指针失败恢复、部分回退失败及失败材料保留继续沿用原有专项测试。

### 更新日志 CI 故障证据

CI 报告为 Windows Python 3.12.10 的 200% 滚轮断言失败。本机 Windows Python 3.12.13 原单项通过；main 与 PR 的界面及该测试源码相同，不能归因为本 PR 新增 UI 缺陷。原测试在多次改变窗口宽度、混合字体及嵌入窗口后，直接比较 Tk 异步估算的 yview 比例，没有同步总高度计算；本次使用 Tk 的 `count -update -ypixels` 显式同步，再保留真实 MouseWheel 事件及滚动断言，同时补验一像素分隔线子控件。修订后布局文件 4 项通过，200% 单项独立重复三次通过。没有删除断言、跳过或增加 sleep。

本地未原样复现 CI 3.12.10 的失败，因此“CI 当时事件为何未产生预期比例变化”的精确运行时原因仍缺少该环境重现证据；本次修复消除可识别的测试同步前提，不能把它表述为已证实所有 Windows 环境的产品缺陷根因。最新提交仍由 GitHub 必需 CI 和人工评审确认。

### 必需迁移的运行目录缺参保护

修复 `apply_update()` 中外层 `runtime is not None` 导致内层缺参检查永不执行的问题。发布计划声明 `database_changed=True` 时，在代码备份、环境准备与代码切换前强制核验运行目录；缺失、空白、不存在或普通文件路径立即拒绝。正常无需迁移的调用继续允许省略该参数。

合成 schema 升级计划通过真实发布校验后，五类无效参数均验证旧代码提交、正式测试数据库字节与环境指针不变，且环境／迁移／安装动作和备份写入未发生。最终新增案例加合法副本迁移及失败回退复核：`7 passed in 21.91s`；事务边界文件初轮 `20 passed in 39.87s`。未执行全量回归、未使用真实用户数据。

### 2026-10-29 环境复用复审修订

- 目标发布清单存在时，环境即使声明未变，也在复用前核验精确解释器路径、Python 版本、锁内包版本、`pip check`，不能由启动探针替代。旧版没有来源清单、依赖文件不变的首次接入同样执行这些检查。
- 没有受管理标记的旧解释器，在全部核验和启动探针成功后才将接纳记录写入 `.git/aplus-update/adopted-environments/`，不修改该解释器目录。每次复用仍重新核验；已受管理环境缺失标记不会转走接纳路径。
- 无逐包哈希锁时，保留既有环境编号格式。存在哈希锁时，编号额外包含其摘要，从而与身份比较字段一致；只修订哈希锁会使用另一最终路径，旧环境及正式环境指针保持原状，直到事务提交。环境变化缺少哈希锁时停止，不退化为不带哈希安装。
- 专项测试使用临时 venv：包版本不符而启动探针本可通过、Python 不符、pip check 失败、启动失败、旧环境成功接纳后再次核验、受管理环境缺失标记、首次清单引入、仅哈希锁改变的真实固定路径建环境和代码安装。所有安装测试的依赖清单为空，只安装临时 venv 自带工具，不访问真实交易数据或修改开发环境。
