# 自动更新事务基础设施验收记录

## 使用影响

普通用户仍从软件内点击更新，不配置额外数据目录，也不手工复制数据库。未来同一 Python 版本内的依赖变化可在旧环境旁边安装并验收；未来数据库结构变化必须先在正式库的一致副本上迁移成功，才允许更新正式库。新桌面未确认启动时，不把新环境记为日常启动环境，并回退本次已执行的代码和数据库变化。

本 PR 只建立上述能力：不修改当前依赖版本、不修改数据库 schema、不读取或迁移真实用户数据，也不修改冻结策略。

## 不变契约

- GitHub main 精确提交及其 `A acceptance` 成功仍是更新许可前提。
- 本地修改、开发分支、受保护路径、冻结清单异常和不安全归档继续阻断自动更新。
- 正式数据库 schema 仍只由 `workbench/store.py` 管理。
- 运行数据目录不随代码版本变化；更新器不删除行情、成交、持仓或研究记录。
- 所有 PR 仍须人工明确批准后才可合并。

## 实施证据

- `release_installation.json` 将 Python 版本、依赖锁摘要、环境编号、schema 目标及迁移范围绑定到发布提交。
- 依赖变化创建旁路虚拟环境，执行锁定安装、`pip check` 和隔离启动探针；成功启动后才写环境指针。
- schema 变化先生成 SQLite 一致备份，在副本运行目标 Store，并检查 `integrity_check`、schema 版本和关键表记录数。
- 正式迁移或启动失败可使用同一事务材料恢复旧代码、原数据库和旧环境选择。
- 启动脚本优先读取受 Git 元数据保护的环境指针，指针无效时回退项目 `.venv`。

## 验证范围

- 定向自动化测试：版本许可、清单摘要、并行环境计划、数据库副本迁移与精确恢复、worker 启动握手及既有 Store 兼容边界。
- R3 完整回归：Windows Python 3.12，`pytest -q --durations=30`，`1622 passed`、`206 warnings`，用时 `867.40s`。
- 静态检查：Python 编译、`git diff --check`、冻结文件相对 main 无改动。

## 未验收与后续边界

- 本轮没有使用真实交易数据；真实数据迁移仅在未来某个正式 schema 变更版本中按该版本的专项验收执行。
- 本轮不下载新的 Python 运行时。Python 版本变化只有在设备已有对应解释器且发布流程另行验收时才继续；可信运行时的签名分发属于后续独立任务。
- GitHub CI 和长期跨版本使用验收不由本地测试替代。
