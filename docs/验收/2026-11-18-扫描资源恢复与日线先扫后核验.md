# 扫描资源恢复与日线先扫后核验

## 范围与不变契约

任务类型：R2 修复。基线为 main `1c0ddaf163aeb8858449a0c56548007c1a3c5039`；实现提交 `fdf9e0ce1bdc85f3c9d6ac150e1f00e07134f807`。本轮按交易员明确限定的最小验证集合执行，用户随后明确授权降低内存要求。

目标：减少资源门槛导致的持续串行；日线一键盘前先保存合格股票结果，再继续缺日核验，必要时补扫。保持冻结六策略、300 根主计算窗口、扫描资格、缓存身份、逐股耐久提交、同源补价、停牌证据和取消语义。未修改 core、冻结清单、数据库 schema、行情协议、加速授权、GUI 或安装器；未修改正式数据库或正式配置。

## 诊断事实和修复边界

- 11/16 扫描子任务 `a7f588382111431a` 的完整结果没有 execution；历史 `784ac4aa9a114b54` 明确为 processes / 2。两次策略和计算指纹相同，实际主窗口没有显著增长。当时的内存、CPU、环境变量和 worker 选择日志缺失，**不能确定历史上究竟是哪项条件关闭了并行**。
- 既有 Windows 日志显示，11/17 北京时间 07:31:03 因 Idle Timeout 进入 Modern Standby，07:49:27 因键盘输入恢复，能够解释 MTR 调用窗口的 1084 秒停顿；不是已经证明的 MTR 算法卡顿。
- 原并行资格只检查一次。首次资源不足后，即使资源恢复，整轮也不会重新尝试。原物理内存估算为保留 1 GiB、每进程 512 MiB，两进程至少需要 2 GiB 可用物理内存。本轮实际机器在释放部分程序后仍约 0.5–1.1 GiB，原预算继续选择串行。
- 原日线一键流程在扫描前逐股核验历史缺日。目标任务已有 222 次核验，首末相隔 239 秒；此过程会延后所有已合格股票的扫描。

## 最小实现

### 扫描资源

`workbench/scan_parallel.py` 把物理驻留预算与 Windows 提交预算分开：

- 物理内存：主进程余量 128 MiB，每个计算进程 128 MiB。
- Windows 可提交内存：保留 512 MiB，每个进程预算 384 MiB。
- 同时取 CPU、显式 worker 上限和两种内存预算的较小值；仍最多 8 个、最多半数逻辑 CPU。显式 1、非法设置、资源探测失败仍走串行；64 只未缓存股票门槛保留。
- 进程运行期间，在取结果前检查物理余量 128 MiB / 提交余量 384 MiB。低于任一值或探测失败，关闭本轮计算进程，继续原串行提交路径。

预算依据：只加载现有计算程序、冻结六策略及数据读取模块，不执行策略计算，Windows 原生进程信息显示实际 Python 子进程驻留 81,313,792 字节、私有提交 292,364,288 字节；连同启动器等进程私有提交共 294,490,112 字节。它只是加载后的占用，不冒充完整计算峰值。提交预算和运行期回退继续保留；没有强制启动固定数量的进程。

`workbench/service.py` 对暂时资源不足执行有限、随扫描推进的重新检查：首次至少间隔 16 只已处理股票，此后至少间隔 64 只；剩余工作不足并行门槛便停止尝试。不会重算已经提交的股票，不重试插件、非 TickFlow、生效快拒、显式串行或不足规模等固定条件，也不重新拉起已故障回退的进程池。

每次保存“扫描并行选择”事件及 parallel_decisions，含 requested、CPU 数、实际可用物理/提交内存、选择原因和位置。父任务摘要也保留 execution / parallel_decisions，子任务完整回执仍为依据。

### 日线一键流程

`workbench/premarket.py`、`workbench/status_maintenance.py`：

1. 原行情更新和资格核验完成后，先扫描合格股票；没有合格股票时不启动空扫描。
2. 原缺日核验和同源补价逻辑在独立 verify_status 子任务中继续执行，保留完整回执及独立耗时。
3. 新增合格快照或资格由部分转为完整时，进入原扫描核验入口补扫；未变化输入复用缓存，原观察唯一身份避免重复。
4. 父任务保留各 scan_jobs 与累计扫描耗时，最终范围状态与结果数量以最后一轮完整范围核验为准。早期缺口和部分结果保留在原子任务，不把同一批股票的数量重复相加。取消保留已提交结果，未知缺日继续显示未完成。

单独“更新行情”的原缺日处理顺序、周线的同步／核验顺序及状态证明规则保持原样。调整的是一键日线编排，不是删除核验工作，也不保证把核验总时间消除。

### 任务期间防空闲休眠

`workbench/task_power.py` 仅在行情、扫描和一键任务执行期间请求 ES_CONTINUOUS | ES_SYSTEM_REQUIRED，正常、取消及异常结束均在同一线程释放；失败留事件，不阻断业务。允许屏幕休眠，不改电源计划或 Windows 全局设置。

这符合 [Microsoft 的活动任务电源请求用法](https://learn.microsoft.com/en-us/windows/win32/power/about-power-management)。本轮没有实际让电脑睡眠或关盖；电池供电、系统策略和主动睡眠仍可能覆盖请求，不能把 API 成功当作整夜 Modern Standby 实机验收。参见 [PowerSetRequest 的 Modern Standby 限制](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest)。

## 唯一一次真实样本前后对照

源为实际运行库的 11/16 子任务快照，SQLite 通过 mode=ro / query_only 读取；只复制行情与公共日历、目录，没有复制账户、计划、持仓或授权。初选 100 份中 8 份需要本次副本未包含的停牌证明，预核验据此排除，**两边统一使用能独立通过资格核验的 92 只**，历史长度 702–1908 根，仍超过 64 只门槛。

本轮只有修复前一次、修复后一次实际扫描。此前内存门槛检查和样本资格检查均在扫描启动前停止，隔离库核对当时 scan jobs 为 0；没有把它们记作性能轮次。

复现工具：`tools/benchmark_scan_resource_recovery.py --snapshot .test-scan-recovery --baseline 1c0ddaf`。同一 Python、同一字节副本、六策略、相同空判断缓存和同样预先准备的质量缓存；没有清理 OS 文件缓存。原 Service / scan_parallel 从基线提交读取。两边统一注入首次资源不足，新版后续探测使用当时真实资源，而非强制 worker 数。这是资源恢复缺陷的受控复现，**不是补造 11/16 历史内存记录**。

耗时减少 **21.87%**，倍率 **1.280×**。恢复时真实可用物理内存 543,592,448 字节，可提交内存 6,401,040,384 字节。未将这个样本的收益外推为全市场 4 倍或 8.3 倍完全恢复。

## 停止条件与未验收事项

最小修复、直接模块及相邻契约通过；一次真实样本前后对照改善且结果一致，故停止验证。没有全量 pytest、全市场扫描、第二轮性能对照、线程数量矩阵、DPI / 布局、无关回测、安装或发布测试。

未验收：正式安装更新、完整交易日夜间实际使用、主动睡眠/关盖/电池策略、全市场耗时。GitHub 必需 CI 由 PR 正常触发；本地证据不能代替 CI 或交易员验收。创建 PR 后不等待 CI，不自动合并。
