# 后续修改的全局约束

每次修改前，请先用交易员能读懂的话说明：改什么、影响哪个使用场景、不应改变什么、拿哪些案例验收。然后才进入实现。

本文件是业务安全约束的权威来源。Codex 的执行方法见 `Codex执行规范.md`，模块职责见 `系统地图.md`，定向测试索引见 `模块测试地图.md`，多人协作与 Git 基线见 `协作分工与开发基线.md`；其他文档不得放宽本文件 A01—A11。

| 编号 | 不可破坏的约束 | 如何检查 |
|---|---|---|
| A01 | 策略、指标和配置默认逐字节保护；只有用户明确点名授权的策略版本可以在限定文件内升级 | frozen_manifest 获批记录、版本号、计算对照与完整测试 |
| A02 | 不打开旧项目的数据库，不以新架构覆盖旧数据 | 所有新持久化只通过 Store；审查跨目录路径 |
| A03 | 研究不修改正式观察或人工计划 | 回测端到端隔离测试 |
| A04 | 没有信号不等于计算失败 | 扫描异常回执测试 |
| A05 | 回测不能给策略未来 K 线，包括指标预计算 | prefix 回放与未来数据扰动测试 |
| A06 | 同一机会更新不生成重复人工计划，不同策略/版本/周期不混淆 | 稳定身份与历史测试 |
| A07 | 新策略默认只研究，不因回测好看自动启用 | 工厂审批门槛测试 |
| A08 | 历史行情版本和报告可追溯 | 内容校验、快照编号、报告参数与版本 |
| A09 | 不自动下单、不把模拟成交当作人工交易 | 检查 UI 文案、数据写入边界 |
| A10 | 任务失败、中断、停止、部分完成和完整完成明确区分 | 任务重启/失败/停止测试 |
| A11 | 桌面 K 线保留各策略自己的标注语义，不能把六类策略统一成同一颗星或重复绘制风险线 | 标注契约测试 + 六类真实观察渲染检查 |

策略变更须由用户明确点名授权对应策略及方向，并增加新版本、获批清单和对照报告；不得通过修改校验值掩盖策略变更。研究层筛选条件必须标注为额外条件，不能说成原策略原生输出。2026-10-14 的授权只解除 MTR 的 `mtr_strategy.py` 与 `mtr_structural_v35.py`，用于 V36.3 光头阳线规则及 V36.4 漏门禁修复，不构成其他策略或文件的通用授权。

数据库结构变更只在 store.py，须增加 schema_version 迁移及旧版数据兼容测试，不能依赖“删除 runtime 重来”。不要用多个 JSON 和数据库重复管理同一个人工状态。

验证按 `Codex执行规范.md` 的风险分级执行：默认运行相关模块测试及必要业务契约测试；涉及冻结策略、正式交易数据、数据库结构、关键跨模块契约或难以隔离影响的高风险变更，执行相应完整安全验证。正式 PR 仍必须通过 GitHub 必需 CI，本地定向验证不能替代该门禁。

增加或改变功能时同步使用说明和版本记录；README 只是入口，不重复维护第二份规则。代码测试、真实数据验证、GitHub CI 和长期实际使用验收必须分别报告。
