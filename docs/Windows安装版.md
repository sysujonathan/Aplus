# Windows 安装版与一键更新

安装版与源码开发分开。功能继续使用现有桌面与 TV 风格图表；首次安装后从桌面 Aplus 打开。
源码版仍使用原启动方式，开发分支、未提交修改及待合并 PR 不参与安装版的版本检查。

## 首次安装

首版目标系统是 Windows 10 21H2（内部版本 19044）及以上的 x64 系统 / Windows 11 x64。
32 位 Windows 不适用此包。安装器默认按当前 Windows 用户安装到
`%LOCALAPPDATA%\Programs\Aplus`，无需 Python 或 Git；不要求关闭杀毒或增加排除项。
安装向导明确提供路径选择，可改到 D 盘等其他位置；升级默认沿用已安装目录。
程序放在非系统盘并不等于数据也在那里：已有数据保留原位置，接续绑定与默认新数据仍在当前用户目录。
重装系统前须另外备份实际数据目录；不能仅凭程序还在 D 盘就认定记录已受保护。
缺少图表 WebView2 运行组件时，使用已验证微软签名的引导程序联网安装；离线且缺少组件时停止并保留原数据。
本机有 Windows 11 实测；用户已反馈修复后的安装包在伙伴 Windows 10 21H2 x64 正常可用。
后者是伙伴实测反馈，并非开发者独立执行的完整验收；未宣称支持更早的全部 Win10 版本。

安装器拒绝有数据库的目标和未识别的非空目录，不能用安装覆盖原源码项目或数据仓。
每个程序版本放入 `app/<版本>`；稳定的 `Aplus.exe` 读取 `current.txt` 启动。
完整性预检通过后才原子切换指针；卸载只清理安装器登记的程序文件。
桌面和开始菜单仍从这个稳定入口启动，图标引用当前版本内的已批准APLUS图标；托盘和原生窗口使用同源图标。
升级完成且新版完整性预检通过后，安装器会独立刷新当前用户桌面已有的快捷方式图标，不依赖“创建桌面快捷方式”选项。
该修复只处理目标精确指向本次安装的 `Aplus.exe`、且使用默认图标或本程序管理图标的链接，包括改过名称的链接；
只修改图标引用并通知 Windows 刷新该链接，保留启动目标、参数和工作目录。不重新创建用户已删除的链接。
修复步骤跳过自定义外部图标、只读/损坏链接和其他安装目录；无法刷新时记录日志，不阻断已验证的安装。
固定任务栏、公共桌面和其他用户的快捷方式不在本次修复范围，不清理 Windows 全局图标缓存。

早期测试包与当前正式包均未配置 Windows 代码签名，系统可能显示未知发布者。代码签名为可选项，
不作为官方更新的必需条件；不要求用户关闭安全软件，也不承诺零安全提示。

## 接续已有数据

首次启动自动检查已知数据位置、当前用户配置、桌面/开始菜单 Aplus 快捷方式及其启动脚本中的路径；
不扫描全盘，不执行发现的脚本。只有一份候选时预选，多份时须明确选择。
可手动选择原 Aplus 程序目录或包含 `workbench.sqlite3` 的数据目录。

识别使用只读 SQLite，核对必要表、schema 1–8、行情日期及业务记录摘要。未知结构、未来 schema、
未收尾事务、运行/排队任务会阻止接续；不能识别的数据不会被替换成空库。
确认前请从托盘完整退出旧版及相关 Web 服务。确认后在独立用户状态目录备份数据库、
校验备份与原件状态，再保存数据绑定；行情文件和原数据目录保留原位，不重复下载。
只有明确选择“首次使用”才可建立新仓，默认位置有文件时禁止覆盖。

备份校验并保存绑定后，欢迎窗口显示“数据已安全接续”、原数据位置及备份位置，
点击“打开 Aplus”进入主界面。桌面快捷方式只代表程序安装完成，不代表数据接续完成。
关闭成功页面后，下次从桌面快捷方式打开会直接使用已接续的数据，不必重复备份或选择。
每次软件内更新在旧程序退出后会再备份一次数据库，异常事务恢复也另存原件；普通启动、检查版本和更新行情不因此重复备份。
当前这些数据库安全备份不自动淘汰，长期更新会累积占用空间；程序旧版本目录的清理并不等于数据库备份清理。
本轮不自动删除用户的任何既有备份。
若接续后主界面未能启动，显示明确错误及日志位置；不能把界面失败误报成数据接续失败。

数据绑定位于 `%LOCALAPPDATA%\Aplus\installed\data.json`，备份位于同目录的 `backups`。
正常卸载和程序更新均不删除这些用户数据。保留当前与上一程序版本；更早版本仅在构建归属清单、文件集合、
文件哈希和进程状态都能确认时清理。未知内容、数据、联接目录及未带归属清单的早期试用版保留；不要手动删除原数据目录。
数据源凭据、原路径依赖及用户自定义旧脚本可能需要单独确认；自动发现不是覆盖任意历史布局的承诺。
迁移按 Store 现有 schema 规则执行，旧数据库备份保留；不在安装器中增加或修改表结构。

已经接续的数据若因断电或异常退出留下事务日志，启动时提供一次明确的恢复确认。
确认后在后台先保存原数据库及 journal/WAL/SHM 文件的原字节快照，再由 SQLite 自身恢复、检查完整性。
恢复目录为上述 backups 下的 recovery-*，包含结果回执。其他 Aplus/Web、数据库连接占用或空间不足时停止，
不手动删除事务日志，不创建替代空库。失败时保留备份与绑定，提示可定位的恢复现场。
尚未接续的旧项目仍只读识别，不通过自动发现擅自修复；先完整退出原程序并完成原端恢复。

## 日常一键更新

启动后与低频后台检查正式发布，按钮出现“一键更新”。点击表示同意更新并重启。
任务或编辑尚未结束时等待空闲；下载、大小/SHA256 校验和安装在后台完成，图表先确认保存再退出。
下载时显示真实字节对应的百分比和进度条；显示 100% 后仍须完成校验和重启准备。
界面繁忙后只显示最新下载进度，不逐条补播旧百分比；失败或重试后不会再接收上一轮的进度提示。
当前下载完整安装包并重启切换程序版本，不是增量补丁或运行中替换代码的热更新。
普通界面不要求阅读更新日志、Git 分支或提交记录。
下载完成后若因编辑窗口或图表保存暂停，重试先重查正式发布及包哈希，并复用未变的已下载包，避免重复下载。
检查或网络失败时回到“检查更新”，不继续显示过期的可更新状态。下载前检查空间，临时文件采用独立名称。
确认新版真实启动成功后删除已验证的下载包，仅保留小体积回执与恢复记录；清理失败不影响新版使用或触发回滚。
旧界面退出后，更新助手持续显示一个“正在更新，请稍候。完成后自动打开。”的简洁弹窗和已用时，
不向用户展示内部细分任务。
使用活动进度条，不伪造百分比，不把助手就绪、安装完成或进程已创建当作主界面启动成功。
提示窗口属于独立更新助手，不阻止旧界面退出；正常完成时在匹配的新版主界面实际显示并确认后关闭。
更新失败则保留明确错误提示，不伪报成功。首次从尚无此提示的旧客户端升级时，原更新助手仍按旧版行为运行；
安装本修复版后发起的后续更新才具备完整助手进度，8→9兼容接续由新版助手接管的阶段也会显示。

更新仅接收官方 GitHub Release 的稳定发布清单与对应安装包，核对完整提交属于 main，
精确提交最新一轮 main push 的 A acceptance 成功；预览清单、PR 检查和未完整上传的包均不获准。
此处依赖官方 GitHub HTTPS 发布身份；独立元数据签名/密钥轮换尚未实现，不宣称具备 TUF 安全模型。
清单标签、完整提交、安装包名称和下载地址必须一致；下载完成和安装前再次验证大小与 SHA256，
安装前重新核对官方最新发布及版本顺序。开发仓库的分支、脏文件、待合并 PR 不参与安装版更新审批。
首版客户端自身只接受 schema 8 发布。针对 PR88 的 schema 9，现提供同版本、同提交的双程序安装包：外层是实际使用 schema 8 的兼容引导程序，内层 `primary/AplusApp.exe` 是 schema 9 主程序；公开清单明确声明 8→9 路径及整包文件清单 SHA256，不把新版主程序伪标成 8。旧客户端一次下载后先确认引导界面启动，引导程序等待旧更新助手结束，再自动调用已安装的新版助手接续，不二次下载或运行 Setup。

接续前原数据库按原字节备份，仅在隔离副本中调用现有 Store 迁移；逐表核对原有字段、记录数和内容（仅允许版本标记变化），完整性检查通过后在原磁盘原子替换。真实主界面与后端均就绪并确认 schema 9 后才完成。失败时，只有数据库仍与刚切换的副本逐字节一致才恢复原件及旧程序；新版已有写入则保留新版数据，由稳定入口恢复新版启动，防止回退丢失新记录。日线缓存保留原位。未知迁移仍阻断，不承诺任意未来 schema 自动兼容。

这取代 PR88 首次交付时要求人工安排跨版本安装的限制。验收须包含未修改的已发行 schema 8 EXE 的真实升级链路，预览环境的发布权威模拟与正式线上验证分开记录。历史边界见 [PA 成长空间验收](验收/2026-10-31-PA成长空间.md)，新路径见 [8→9 安装版接续验收](验收/2026-10-31-安装版八到九自动接续.md)。

版本使用北京时间日期与当日发布序号（如 `2026.10.30.6`），与 PR 编号无关。
发布序号由日期与当日序号唯一换算；应用、稳定启动器、Setup 文件属性和更新界面共用这份身份。
历史源码目录无法匹配已记录发布提交时显示“源码版 · 提交短号”，不再套用过时的 PR53 编号。
早期 .1–.5 试用版仍有旧签名拦截，首次接入新规则须完整退出后运行新 Setup 升级原安装目录，
无需先卸载，也不需要搬数据；之后才可由软件内更新接收符合新规则的正式发布。

更新助手在旧进程退出后备份数据、调用安装器、直接启动新版本，等待真实后端和桌面 ACK。
失败保留数据并恢复旧代码；新进程仍存活但启动未确认时不强杀、不盲目回退，后续启动继续核对。
安装中阶段、旧 EXE 哈希和更新路径在执行 Setup 前持久化。中断后安装器不再活跃、新版也未运行且旧版身份
可验证时，稳定启动器独立恢复旧指针；不依赖可能缺失/损坏的当前版本 EXE。缺少阶段或旧版身份的未知记录
保留现场并停止，不以删除 pending 猜测恢复。同 schema 的恢复仅切换代码指针；已声明的 8→9 迁移恢复另核对绑定、备份及原件哈希，按上述规则恢复原字节或继续新版启动，不能混用两种恢复方式。
稳定启动器由后续 Setup 受控替换；运行中的启动器通过独立命名锁阻止安装，不强杀或安排重启后强制替换。
恢复只保留稳定原生启动器这一套实现；测试实际编译、运行该启动器并检查不可信记录不改变现场。
这不承诺所有未来数据库迁移均可通过退回旧 EXE 恢复。

卸载精确清理安装器生成的 current/previous 指针，允许随后重装到同一目录；不会递归删除未知文件或用户数据。
安装前检查程序目标子目录中的 workbench.sqlite3，遇到数据或目录联接时停止，不通过覆盖解决。

## 构建与发布

本机探索可先不推送。开发使用独立工作区和测试数据，最终修改经 PR、人工评审、merge 与完整 main 验收。
构建环境使用 Python 3.12、`requirements-lock.txt` 与 `packaging/requirements-build.txt`。
官方 Inno Setup 7.1.1 编译器的下载地址见构建工作流，执行前验证 Pyrsys B.V. 签名。

```powershell
python tools/build_installer.py --iscc <ISCC.exe路径>
```

生成 `dist/installers/AplusSetup-<版本>-x64.exe` 及清单；本地默认预览。
`--official` 仅允许干净、精确官方 main 且对应 push CI 成功的代码。
正式构建可显式提供日期版本与单调发布序号，不使用 PR 号或提交计数。
已有发布者证书时可给构建器传 `--signtool` 与 `--certificate-thumbprint`，先签应用和启动器，
编译 Setup 后再签最终安装器，最后生成最终包哈希；不会在源码中保存私钥或密码。
`.github/workflows/installed-release.yml` 在官方 main 的 push 验收成功后自动构建、校验并发布正式安装包。
只有官方仓库、main 分支及对应精确提交的最新一轮 `A acceptance` 成功才获准；PR 检查、分叉仓库事件、
失败/取消的验收均不能发布。手动运行也须满足同一门禁，不改变 A acceptance 的必需检查、触发或完整测试范围。
只读构建任务先核对是否已经发布该提交，避免重复构建；通过真实 EXE 行情通信、冻结校验及 GUI/WebView 冒烟后，
上传该次构建的 artifact。独立发布任务只接收同一构建任务输出的 artifact ID 与精确提交，
仅该任务取得 `contents: write`，使用 GitHub 自带的短期令牌，不要求维护者配置个人令牌或购买证书。
版本分配在独立的 `identity` 作业中执行：GitHub 只有具备推送权限的调用者才能列出草稿，因此该元数据作业
使用 `contents: write`，先核验精确已验收 main，再分页读取正式版和草稿占用的版本号，分配未占用的新号。
该作业不安装项目依赖、不执行编译器或构建包，checkout 不保留凭据；真正构建作业继续只读，按输出精确提交检出并重新验收。
同一工作流全程串行占用既有发布并发组；元数据查询失败则停止，不把失败视为空列表。
发布工具仍仅续做身份、提交和已上传字节都一致的草稿。旧草稿/标签/资产不覆盖，身份或字节不同仍拒绝；
新构建会避开草稿已占用的版本，而不是要求用户处理冲突。

正式发布不强制购买 Windows 签名证书。使用 `tools/publish_installer.py <Setup路径> --manifest <latest.json路径>`：
再次验证精确 main、对应 push CI、包大小与 SHA256；先创建草稿并上传，再次确认主线后才设置 latest。
若已配置签名，可额外传 `--signtool` 检查 Setup；声称全包已签名时仍须分别验证内层两个 EXE，
不能由外层签名推断内层。微软 WebView2 引导器与 Inno 编译器的签名验证仍保留。
自动发布先创建草稿、上传，再真实下载草稿中的清单与 Setup 校验；公开前再次核对当前 main、最新一轮 push 验收和版本顺序。
主线已前进时保留草稿，继续提供上一正式版，等待新主线验收；绝不把过时构建抢发为 latest。
相同草稿可用原构建产物续做缺失上传，已有文件不覆盖；同一已公开包重试不会重复发布或把 latest 改回旧版。
公开后再用客户端实际的 `load_manifest` 核对线上发现，保存小体积 published 回执供追溯。
完整工作流重跑会跳过已正式发布的精确提交；上传中断后优先重跑失败的发布任务，复用原 artifact。
已发布版本不覆盖；需要人工恢复时可运行发布工具并加 `--expected-commit <完整SHA> --resume --verify-online`，
仍执行上述门禁，不能用本地预览包替代。
新版本标签尚未创建时，通过精确 Git reference 接口确认不存在；只有该查询的 404 视作正常新发布。
已有标签仍解析到最终提交核验，包含附注标签；权限、网络、限流、422 等错误不能当作“没有标签”放行。
发布工具按 UTF-8 读取 gh 的 JSON，避免 Windows 系统代码页把含中文的提交响应读坏。
正式发布前须用对应主线产物完成安装/真实升级演练并核对数据保护；本地模拟官方发布的演练不等于真实线上升级闭环。

冻结 core/config 以 `py` 收集模式部署，原文件按字节随包保存并作为实际导入模块，
不修改冻结清单，也不放置另一套未校验的 core/config 编译模块替代执行。
安装版加载器在每次导入冻结模块时校验后直接编译同一份源码字节，不走未校验 pyc 缓存；
自检还核对实际策略类的文件位置与加载器。
交付需核对包内冻结文件、实际模块路径与资源，而不只检查构建日志。

行情连接由安装版 EXE 的专用子进程入口运行，通过父子进程管道收发请求，不重复打开桌面。
构建安装包前必须通过真实无控制台 EXE 的离线行情通信检查，包含取消、错误回执和正常退出；
检查不访问供应商、不读取正式数据。此检查与界面/TV 冒烟分别验证，不以桌面能打开代表行情可更新。
